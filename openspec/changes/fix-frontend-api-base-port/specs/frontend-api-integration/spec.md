## MODIFIED Requirements

### Requirement: 前端 SHALL 从独立 origin 提供服务

前端页面 SHALL 由独立于后端的静态服务器托管，并通过 HTTP 协议以真实 origin 访问。前端 SHALL NOT 以本地文件协议直接打开，因为该方式产生的来源标识无法通过跨域白名单校验。

#### Scenario: 前端通过独立静态服务器访问

- **WHEN** 开发者按约定启动前端静态服务
- **THEN** 浏览器通过形如 `http://localhost:<端口>` 的地址访问页面

#### Scenario: 以文件协议打开时提交请求

- **WHEN** 用户以本地文件协议打开前端页面并触发接口请求
- **THEN** 该请求的来源标识无法匹配白名单，浏览器阻止脚本读取响应；此为该访问方式的已知限制，不作为受支持的用法

## ADDED Requirements

### Requirement: 前端调用的后端地址 SHALL 与后端监听端口一致

前端页面 SHALL 向一个明确声明的后端地址发起请求，该地址 SHALL 与后端实际监听的端口保持一致。

后端监听端口的**权威来源** SHALL 是后端配置文件中的服务端口项（`backend/configs/config.yaml`
的 `server.port`）。任何其他地方出现的同一取值——包括前端页面中的后端地址常量、
以及编排文件中用于提示的端口变量——SHALL 与该权威来源一致，SHALL NOT 各自独立取值。

此项约束的目的是消除"同一事实在多处各说各话"：端口取值在三处重复出现时，
若没有一条规格指定哪一处是权威，任一处漂移都不会产生任何信号，页面会静默地连不上后端。

#### Scenario: 默认配置下页面可用

- **WHEN** 开发者按默认配置同时启动后端与前端静态服务并打开页面
- **THEN** 页面发起的健康检查与列表请求均到达后端并返回成功，页面不显示服务不可用

#### Scenario: 页面中的后端地址与后端配置一致

- **WHEN** 核对前端页面中的后端地址与后端配置文件的监听端口
- **THEN** 两者的端口取值相同

#### Scenario: 编排文件的提示端口与后端配置一致

- **WHEN** 核对编排文件中用于提示的后端端口变量与后端配置文件的监听端口
- **THEN** 两者的取值相同，使编排输出的提示不误导开发者

#### Scenario: 后端配置被修改时其余取值随之更新

- **WHEN** 后端配置文件的监听端口发生变更
- **THEN** 前端页面中的后端地址与编排文件中的提示端口同步更新；
  该同步是本次变更类型下必须一并完成的工作，而非可选的后续优化
