## Context

动机与范围见 `proposal.md`；系统必须表现出的行为见 `specs/` 下两个能力规格。本节只记录
影响「怎么做」的现状与约束。

- **前端现状**：`frontend/` 是独立仓库（`github.com/snzysnk/ChinaTravel-frontend`），
  当前只有 `index.html`（8987 字节，内联 CSS + 内联 JS）+ `.gitignore`。零构建、无模块化、
  无类型检查。仓库历史仅两次提交。其文件头注释已写明「页面逻辑增长时应评估迁移到带构建的
  前端工程」，且明确警告不要继续往该文件堆代码。
- **前端与后端的唯一契约**：响应信封 `{code, msg, data}`，HTTP 状态码恒为 200，业务成败
  只看 `code`。当前 `index.html` 的 `request()` 函数是全页唯一的请求入口与信封解析点。
- **本机工具链已确认**：`node v26.8.2`、`npm 11.19.1`、`docker 27.4.0`（**无 compose 插件**）。
  `pnpm` 未安装。
- **仓库拓扑硬约束**（来自 `openspec/config.yaml`）：本变更是 workspace 仓库中的记录，
  但前端代码的提交落在 `frontend` 仓库；workspace 仓库只更新 submodule 指针与仓库级文件
  （`Makefile`、`AGENTS.md`、`openspec/config.yaml`）。
- **既有约定**：`openspec/config.yaml` 的 YAGNI 条款要求新增依赖说明理由；
  「每个方法必须有注释，不易理解的业务逻辑补解释性注释」同样适用于前端源码。
- **已知历史问题**：端口取值在「后端配置 / 前端常量 / Makefile 提示变量」三处重复，
  已实际漂移过一次（`fix-frontend-api-base-port` 变更；前端仓库 commit `a03714d` 把
  `API_BASE` 从 8080 改为 18080）。这直接催生了本变更的决策 4。

## Goals / Non-Goals

**Goals:**

- 让前端从「验收页」升级为「可持续加页面的工程」，且升级后现有页面行为不变。
- 用类型系统把「AI 生成的代码调用了不存在的接口方法」这类错误拦在运行之前。
- 从机制上消除端口取值多处重复的问题，而非继续用「记得同步修改」的纪律来约束它。
- 把前端目录约定固化进 spec，使「新代码放哪」不再是一次性决策。

**Non-Goals:**

- 不改视觉与交互：迁移是搬运，不是重做。`index.html` 现有的界面、配色、交互流程原样保留。
- 不引入路由、状态管理、UI 组件库、CSS 框架、前端测试框架（理由见决策 5）。
- 不做容器化与部署编排（理由见 `proposal.md` 的「不在本次范围内」）。
- 不调整后端技术栈（结论见决策 8）。
- 不建立前后端类型自动生成链路（理由见决策 6）。

## Decisions

### 1. 前端框架：Vue 3，而非 React

**结论**：Vue 3 + 单文件组件（SFC）+ 组合式 API。

**理由**：本项目的协作模式是「AI 生成代码、单人审阅与维护」（需求方在探索阶段明确：要快在
「AI 写出的东西我能看懂、能改、能接管」这一段）。在该模式下，**首要指标是「错误是否暴露在
阅读层面」**，而非「模型一次写对的概率」。

- React 的错误倾向于藏在运行时行为里：`useEffect` 的依赖数组漏一项、闭包捕获了旧值、
  重渲染时机不符预期。这些代码**语法完全正确、模板语法也不难**，但行为是错的，
  且无法通过阅读代码发现，必须理解 React 的渲染与闭包模型才能定位。
- Vue 的响应式依赖是显式声明的（`computed` / `watch` 的依赖来源），SFC 把模板、逻辑、
  样式分块，模板是声明式的。AI 写错时，错误更容易在阅读时被肉眼抓住，调试门槛落在
  「懂业务」而非「懂框架内部模型」。

**已考虑的替代**：React。其优势是训练语料量级更高（npm 月下载量 React 约 7.38 亿、
Vue 约 6680 万，比值约 11:1；GitHub `facebook/react` 约 250,862 stars，
`vuejs/core` 约 54,479 stars），模型对 hooks/JSX 的条件反射更强。被否的原因：
语料密度影响的是**首次生成的成功率**，而 Vue 的「语法糖」优势影响的是**错误被发现的成本**。
在单人维护下，后者是一旦生成就要长期承担的，前者只是一次性的。若团队扩大、或有专人只做
前端产出而不承担维护，结论应重新评估。

**代价**：Vue 语料较少，AI 生成的 Vue 代码可能需要更多一轮修正。缓解方式是类型检查
（决策 2）会在修正前就指出具体错误位置，而不是留到运行时。

**不采用的形态**：不使用「CDN 引入 Vue + 继续单 html 文件」。该形态既保留了零构建的全部
债务，又落入了 AI 语料最稀疏的组合（无构建 + 全局 Vue 对象 + 选项式 API），是最差选项。

### 2. 语言：TypeScript，且设为强制

**结论**：源码用 TypeScript 编写，类型检查纳入构建流程，类型错误阻止产出。

**理由**：这是本变更中**唯一能在代码运行之前拦截 AI 幻觉的机制**。AI 生成前端代码时最典型
的失败模式是调用不存在的方法（例如凭空写出 `api.getDestinationById()`，而接口层只有
`getDestination()`）。在 JavaScript 下，这类错误只有运行时才暴露，且往往在某个分支里——
单人项目中可能很久都碰不到那条分支。TypeScript 下 IDE 与类型检查立刻标红并指出位置。

**这是「AI 生成、人工审阅」模式相对「人写代码」模式收益被放大的地方**：人写代码时很少
调用自己没定义的方法，因此类型系统的边际收益有限；AI 写代码时这是高频失败模式。

**代价**：需要维护接口响应的类型声明，与后端结构存在手工同步成本（见决策 6）。

### 3. 构建工具：Vite

**结论**：Vite + `@vitejs/plugin-vue`。

**理由**：Vue 官方推荐且为脚手架默认；提供开发服务器、热更新、生产构建三件事；
配置量极小（本项目只需转发配置与 `base` 两项）。没有值得比较的替代品。

**已考虑的替代**：不用构建工具（保持现状，被决策 1 的「不采用的形态」否掉）；
webpack（配置复杂度对本项目规模而言纯属负担）；Rspack / esbuild 直连（收益是构建速度，
而本项目前端规模下构建耗时本就不是瓶颈，引入非常规工具反而降低 AI 语料密度）。

### 4. 开发期跨域：经开发服务器转发，前端不持有后端地址

**结论**：前端以相对路径（如 `/api/destinations`）发起请求；开发服务器把 `/api` 前缀转发到
后端。前端源码中不出现后端端口。

**理由**：这是本变更中**收益最实的一条**——它把「端口的一致性」从**纪律问题**变成**结构问题**。
当前端口在三处重复（后端 `configs/config.yaml`、前端 `API_BASE`、`Makefile` 的 `BACKEND_PORT`），
已实际漂移过一次（见 Context 中的历史问题）。转发方案下，前端不再持有该取值，
漂移的触发点从「三处中任一处」收敛为「转发目标一处」。

**连带收益**：前端产物在开发与生产环境使用同一套相对路径（生产由反向代理转发），
无需按环境注入不同的 API 地址，因而不需要 `import.meta.env` 之类的环境分支。
这消除了「构建时注入地址」这一整类配置管理问题。

**已考虑的替代**：保持直连 + `API_BASE` 常量，继续靠规格纪律同步三处取值。被否：
`fix-frontend-api-base-port` 变更的存在本身说明该纪律已经失守过一次，
用「更严格地遵守同一套纪律」来防它再犯，不如换掉机制。

**代价**：
- 后端 CORS 白名单在开发期不再被实际触发（请求变成同源）。这**不构成问题**——CORS 中间件
  对生产环境的跨域部署仍有意义，且其测试（`middleware/cors_test.go`）不依赖前端。
  但需承认：**开发期不再能顺便验证 CORS 配置**，这是真实的观测能力损失。
- 前端构建配置中多了一处后端端口取值（转发目标），`Makefile` 的提示端口仍在。因此
  取值重复从三处降为两处，而非归零。

### 5. 不引入路由 / 状态管理 / UI 库

**结论**：本次不引入 `vue-router`、`Pinia`、UI 组件库、CSS 框架、前端测试框架。

**理由**：直接落实 `openspec/config.yaml` 的 YAGNI 条款。当前前端只有一个页面、两个接口、
无跨页面共享状态。上述依赖在此时收益为零，而每一个都会引入新的目录约定与决策点，
与「先把工程骨架立稳」的目标相反。

**触发条件**（写在此处以避免下次重议）：出现第二个页面且需要跳转时引入路由；
出现两个页面共享且需跨页面保持的状态时引入状态管理；出现表单、表格等成规模的交互组件时
评估 UI 库。

### 6. 信封类型：前端手工声明，不做自动生成

**结论**：接口响应的信封与各接口的数据类型在前端以 TypeScript 手工声明，与后端结构对齐。

**理由**：前后端是**两个独立仓库**，自动生成需要在两端之间建立代码生成链路（后端导出
OpenAPI/JSON Schema → 前端生成类型），这会引入：后端新增一个生成步骤与依赖、
前端新增一个生成步骤、以及生成产物是否入库的决策。当前接口只有两个、数据结构稳定，
手工声明的成本远低于链路建设与维护成本。

**已考虑的替代**：OpenAPI 生成。在本项目当前规模下明显过度；待接口数量增长到手工同步
开始频繁出错时，作为独立变更引入。届时的切入点应是后端导出 OpenAPI 文档，
而非自定义生成脚本。

**代价（必须被接受，而非忽略）**：后端改动响应结构时，前端类型**不会自动报错**——
两者是手工同步的，存在静默不一致的可能。缓解方式是决策 7 的验收项：迁移后必须做一次
端到端人工验收，确认前端实际解析到的字段与后端返回一致。

### 7. 迁移方式：原样搬运，先验证链路再谈改进

**结论**：`index.html` 的界面、样式、交互流程原样迁移到新工程的页面组件中，
`request()` 的信封解析逻辑原样迁移到接口层。迁移完成后页面行为应与迁移前逐项一致。

**理由**：迁移与重写混在一起时，一旦页面出问题，无法判断是「迁移引入的」还是「新写的
逻辑有 bug」。原样搬运把变量收敛为一个：链路是否断。这也让验收标准客观——对照迁移前的
页面逐项检查，而非主观判断「看起来没问题」。

**配套**：`index.html` 顶部关于「零构建的限制」与「以文件协议打开不受支持」的注释内容，
在迁移后仍有价值的部分（如文件协议限制）应保留在新工程的对应位置，而非随文件一起丢弃。

### 8. 后端技术栈：保持 Gin（附带结论）

**结论**：本变更不调整后端技术栈，继续使用 Gin。

**理由**：本项目已在 Gin 之上建成了实质性的约定资产——响应信封、三个自研中间件
（访问日志 / CORS / 带信封的 Recovery）、领域垂直分包布局、五项已归档能力规格、
`AGENTS.md` 中的三条硬约束。更换框架的成本不是「重写 handler」，而是**推翻这套资产**
并重建等价物，而 GoFrame/Beego 提供的约定并不比现有的更贴合本项目需求
（尤其是「HTTP 恒 200 + 业务 code」这一非常规契约，需要自定义中间件才能实现，
三个候选框架在此点上并无差异）。

从 AI 生成质量看，Gin 的语料显著更密（GitHub 约 89,274 stars，对比 GoFrame 约 13,286、
Beego 约 32,426），且 Beego 的最大风险是模型大量记忆其 v1 时代 API，可能生成混用两代
API 的代码——这是最难定位的一类 AI 幻觉。

**重新评估的触发条件**：若后端出现「大量 CRUD + 复杂 ORM + 多数据源」的规模化需求，
且愿意整体接受某个框架的全家桶约定，届时以**独立的、由 ORM 选型驱动的变更**重新评估。
不构成现在更换的理由。

**记录方式**：本决策的核心结论（保持 Gin）应写入 `AGENTS.md` 的技术栈描述，
使下次不必重新论证。

## Risks / Trade-offs

- **[迁移引入行为回归]** → 决策 7 的原样搬运 + 迁移前后逐项对照验收；不借迁移改功能。
- **[开发期不再验证 CORS 配置，跨域问题推迟到生产暴露]** → 在 `tasks.md` 中保留一条
  可选的交叉验证步骤：以直连方式（临时绕过转发）发起一次请求，确认后端白名单仍包含
  开发服务器来源；同时保留 `backend/internal/platform/middleware/cors_test.go` 作为
  契约层保障。
- **[前端类型与后端结构静默不一致]** → 决策 6 已显式接受该代价；缓解方式为端到端人工验收，
  并在接口层类型声明处注明其权威来源是后端响应信封规格。
- **[引入构建链后「克隆即可访问」的开发体验变差（首次需装依赖）]** → 在 `README.md` 与
  `AGENTS.md` 中明确首次启动步骤；`Makefile` 的 `serve-frontend` 目标不得隐式依赖
  未安装的依赖，应在缺失时给出明确提示而非难以理解的报错。
- **[`Makefile` 是 workspace 仓库文件，而前端命令属于前端仓库，编排边界可能变模糊]** →
  在 `Makefile` 中用注释说明：前端目标通过 `$(FRONTEND_DIR)` 进入前端仓库执行其自身命令，
  具体命令由前端仓库的 `package.json` 定义，workspace 层只做进入与提示，不复制命令细节。
- **[Vue 语料较少导致 AI 生成需更多轮修正]** → 用类型检查（决策 2）把修正点从「运行时
  行为异常」前移到「编译期明确报错」，缩短定位时间。
- **[node 版本要求]** → 本机为 `node v26.8.2`，远高于 Vite 与现代 Vue 工具链的要求；
  应在 `package.json` 的 `engines` 与前端 `.gitignore` 中明确最低版本与忽略规则，
  避免协作者环境不一致。

## Migration Plan

**执行顺序**（与 `tasks.md` 一致）：前端仓库建立工程骨架 → 迁移信封解析与接口层 →
迁移页面 → 移除旧的零构建文件 → 更新 workspace 仓库的编排与文档 → 端到端人工验收。

**跨仓库提交边界**（依 `openspec/config.yaml` 的仓库拓扑硬约束）：

| 改动内容 | 提交落点 |
|----------|----------|
| 前端工程骨架、源码迁移、构建配置 | `frontend` 仓库 |
| `Makefile`、`AGENTS.md`、`openspec/` | workspace 仓库 |
| submodule 指针更新 | workspace 仓库（前端仓库提交完成之后） |

**回滚策略**：前端仓库的改动的集中在新增文件与 `index.html` 的移除，回滚即
`git revert` 对应提交，`index.html` 随之恢复；workspace 仓库回滚 `Makefile`、`AGENTS.md`
与 submodule 指针。两端均无数据迁移、无外部依赖的持久化状态，回滚无残留。
**注意**：须先回滚 workspace 的 submodule 指针，再回滚前端仓库，否则指针会指向不存在的提交。

## Open Questions

- **开发服务器端口是否变更**：当前 `Makefile` 的 `FRONTEND_PORT` 为 5173，而 Vite 默认端口
  也是 5173。保持该值是自然选择，但需在 `tasks.md` 中确认二者未冲突，
  以及后端 CORS 白名单（`http://localhost:5173`）在该取值下仍然有效。
  此问题不影响 spec 与任务拆分，实现时确认即可。
- **是否把 `vue-tsc` 的类型检查接入 `Makefile` 的前端目标**：倾向接入（否则类型检查
  不会被实际执行，决策 2 的价值落空），但具体目标命名与是否与 `make test` 合并，
  留待实现时按顺手程度决定，不影响 spec。
