## Context

动机与范围见 `proposal.md`；系统必须表现出的行为见 `specs/` 下五个能力规格。本节只记录影响"怎么做"的现状与约束。

- 仓库为空：无 `go.mod`、无任何 Go 文件、无首次提交。不存在需要兼容的历史代码或已归档 spec。
- 本机工具链已确认：`go1.24.3 darwin/arm64`、`node v26.8.2` / `npm 11.19.1`、`docker 27.4.0`（无 compose 插件）。本机**没有** `mysql` / `psql` / `redis-cli` 客户端，因此任何依赖真实数据库的方案在 C1 阶段都无法本地验证——这是选择内存实现的重要现实约束。
- 项目既有约束（来自 `AGENTS.md` 与 `openspec/config.yaml`）：KISS/DRY 且可读性优先；不引入非必需依赖，新增依赖必须在 `proposal.md` 说明理由；每个方法必须有注释。
- 交付边界经探索阶段确认为 **C1 内存版最小闭环**：不落库、不鉴权、不做业务建模、前端不用构建工具。

## Goals / Non-Goals

**Goals:**

- 一次跑通 `静态前端 -> CORS -> Gin 路由 -> 处理函数 -> 业务层 -> 仓储层` 的完整链路，并让跨域、信封格式这两个最容易在集成期翻车的点现在就暴露出来。
- 把"代码放哪、接口长什么样、配置从哪读、日志往哪写"四个长期问题在本变更内一次性定死，使后续领域可按同一套规矩增量添加。
- 让"将来接入数据库"这件事被表达为一个可替换的实现，而不是一次结构性重写。

**Non-Goals:**

- 不建立"通用脚手架/模板工程"能力：本变更产出的结构服务于 ChinaTravel 本身，不为"换个业务名就能开工"做抽象。
- 不在本变更内定义业务领域模型（目的地数据仅为链路验证载体，不代表最终业务模型）。
- 不追求生产级完备：无限流、无熔断、无链路追踪、无健康探针的编排集成、无容器化。
- 不为 handler 之外的层建立测试基线（理由见"决策 10"）。

## Decisions

### 1. 目录结构：领域垂直分包（feature-first），而非技术分层

```
ChinaTravel/
├── go.mod                     module github.com/xieruixiang/ChinaTravel
├── Makefile
├── configs/config.yaml
├── cmd/server/main.go         进程入口
├── internal/
│   ├── bootstrap/app.go       对象图装配 + 中间件 + 路由注册
│   ├── platform/              跨领域公共机制
│   │   ├── config/config.go
│   │   ├── logger/logger.go
│   │   ├── middleware/        访问日志 / CORS / Recovery
│   │   └── response/envelope.go
│   ├── health/handler.go
│   └── destination/           示例领域
│       ├── model.go
│       ├── repository.go      接口 + 内存实现
│       ├── service.go
│       ├── handler.go
│       └── handler_test.go
└── frontend/index.html
```

**理由**：本项目预期会持续增加多个业务领域。技术分层（`handler/` `service/` `repository/` 各一个目录）在只有一个领域时就会产生空目录，且每加一个领域都要同时改动四个目录；垂直分包让新领域=新包，领域间天然隔离。

**已考虑的替代**：技术分层 + `cmd/internal/configs/pkg` 骨架。被否，因为 C1 下 `repository/` 必然为空壳（无数据库），违背"不摆空目录"的意图。

**代价**：跨领域机制需要一个显式的 `platform/` 包来承载，比技术分层多一层概念。这是为将来增量添加领域付出的前置成本，在本变更内即被 `config`/`logger`/`middleware`/`response` 四者填满，不构成空壳。

### 2. 响应信封：统一信封 + HTTP 恒 200 + code 分段

信封结构固定为 `{code, msg, data}`，HTTP 状态码恒为 200，`code` 采用五位分段（前 3 位表 HTTP 语义，后 2 位表业务序号）。C1 阶段只需 `0`（成功）与一个 `404xx`（资源不存在）两个常量，分段规则以注释形式记录，**按需增补常量**，不预先定义用不到的码。

**理由**：这是明确的产品取向——前端只看 body 的 `code`，获得统一的错误处理入口，不必为每个接口各写一套判断。

**代价（必须被接受，而非被忽略）**：网关、Nginx 访问日志、APM/Sentry 等基础设施层只能看到 200，业务失败在基础设施侧**完全不可见**。缓解措施是访问日志中记录真实的业务 `code`（见 `observability-baseline`），使失败仍可在应用日志中被检索。

**强制配套**：`Recovery` 中间件**必须**替换为输出信封的版本。默认的 `gin.Recovery()` 返回 500 + 空 body，在信封契约下会导致前端 `JSON.parse` 直接抛异常——这不是可选项。

**替代方案**：裸对象 + 真实 HTTP 状态码。更符合 REST 惯例、基础设施可观测性更好，但不符合本项目"前端统一解析"的取向。

### 3. code 常量：按需定义，规则用注释承载

只定义当前用得到的常量，分段规则（`400xx`/`401xx`/`403xx`/`404xx`/`500xx`）以注释形式写在常量块内，使后续新增常量有章可循，同时不引入 C1 用不到的声明。

**理由**：直接落实 `AGENTS.md` 的 YAGNI 条款；同时避免"C1 只有两个码却要维护八行常量"的仪式感。

### 4. 配置加载：yaml.v3 + `APP_*` 环境变量覆盖

`configs/config.yaml` 提交进仓库作为默认值来源；`APP_` 前缀 + 下划线 + 大写 的环境变量覆盖同名项；数组型配置以英文逗号分隔覆盖。不使用 viper。

**理由**：`yaml.v3` 无传递依赖、体积小；viper 的强项（多格式、远程配置、热重载）在 C1 收益为零。环境变量覆盖解决"CORS 白名单在不同环境不同、且不应提交进仓库"的实际需求。

**替代方案**：纯环境变量（零依赖）。被否，因为数组型配置用环境变量表达别扭，且"配置怎么加载"是框架骨架的一部分，早立规矩优于后补。

### 5. 日志：标准库 `log/slog` + 自写访问日志中间件

使用 `gin.New()` 而非 `gin.Default()`，通过自写中间件产生访问日志，使全部日志（应用日志 + 访问日志 + panic 日志）走同一个 `slog` 出口、同一格式。

**理由**：零新增依赖；Go 1.24 下 `slog` 是官方结构化日志入口。保留 `gin.Default()` 会导致框架自身格式的日志行与 `slog` 输出混杂，正是 `observability-baseline` 规格所禁止的"多路日志"。

**代价**：需要自写约 20 行中间件。该代码为纯标准库，且换来了"框架提供统一日志出口"这一实质能力。

**替代方案**：zap / zerolog + 保留 `gin.Default()`。最省事，但引入依赖且无法满足"格式统一"的规格要求。

### 6. 依赖注入：集中装配（构造函数归各包）

各领域包导出 `NewXxx(...)` 构造函数（Go 惯例，且测试需要直接构造），但**谁 new 谁**全部集中在 `internal/bootstrap`。不引入 wire / fx。

**理由**：C1 需要连接的对象只有三个（仓储→服务→处理函数）。wire/fx 的收益要到依赖图有几十个节点才显现，现在引入纯属仪式。集中装配使 `cmd/server/main.go` 只承担进程生命周期职责，依赖变多时也不会膨胀。

**替代方案**：构造函数调用散落在 `main.go`（依赖增多后入口文件膨胀）；wire（需 `go:generate` 纪律 + 生成步骤）；fx（反射，调试绕，对 C1 严重过度）。

### 7. 微服务边界：`bootstrap.Build` 返回未绑定端口的处理器

装配函数返回 `*gin.Engine`（或等价的 `http.Handler`），端口绑定与监听由 `main.go` 负责。

**理由**：这是让 `http-server-bootstrap` 规格中"测试无需真实端口"可被满足的结构前提——测试可直接对返回的处理器发请求。同时让 `main.go` 的所有权边界清晰：它管进程，`bootstrap` 管对象。

### 8. 优雅关闭：包含，且设等待上限

`main.go` 通过 `signal.NotifyContext` 捕获 `SIGINT`/`SIGTERM`，调用 `http.Server.Shutdown` 并设置超时上限。

**理由**：约 15 行纯标准库代码，换来一个不会在重启时切断进行中请求的进程。属于"框架骨架该有的东西"。

### 9. 仓储：接口 + 内存实现，示例数据放在内存仓储内

`destination/repository.go` 定义仓储接口与其内存实现，`GET /api/destinations` 的数据存放在内存实现中，而非硬编码在处理函数里。

**理由**：这样 `handler -> service -> repository` 三层在 C1 就被真实跑通，而不是"两个没被验证过的空层"。将来接数据库时，只需新增一个实现同一接口的类型并在 `bootstrap` 中替换构造，`handler` 与 `service` 一行不用改——这正是选择垂直分包所要兑现的承诺。

**已考虑的替代**：硬编码在 handler 中（最省事，但使分包形同虚设，且无法验证 JSON 序列化之外的链路）。

### 10. 测试：仅 handler 层，标准库 testing

只对 handler 编写 HTTP 契约测试（构造处理器 → 发请求 → 断言状态码为 200 且 body 的 `code`/`data` 结构符合信封）。不引入 testify。

**理由**：信封契约是"前端只看 code"取向下唯一的守门人，格式一旦失守前端全线崩溃，因此这一层的测试收益最高。而 C1 的 service 层几乎只是透传（测它等于测"函数返回参数"），仓储层是几行 map 读写，两者的测试收益接近零。按 KISS/YAGNI，这两层留白。

**已知空白**：跨域行为无法用进程内测试可信地验证（它由浏览器强制），因此 CORS 只能通过人工验收（见 `tasks.md` 的验收步骤）。这是本设计的**有意取舍**，不是遗漏。

## Risks / Trade-offs

- **[信封 B 使基础设施层丧失可见性]** → 在访问日志中记录业务 `code`，使失败仍可按 code 在应用日志中检索与告警；`proposal.md` 已显式记录该代价。
- **[垂直分包在只有单领域时显得绕]** → 由 `platform/` 包在 C1 即被四个模块填满来缓解；若后续领域数长期维持为 1~2 个，此决策可重新评估（届时迁移成本仍可控）。
- **[内存实现给人"已经能用了"的错觉]** → `repository.go` 与 `model.go` 的注释中显式标注"示例数据，非持久化，进程重启即丢失"；`proposal.md` 的"不在本次范围内"已单列持久化。
- **[CORS 无法自动化验证，只能人工验收]** → 在 `tasks.md` 中给出可复制的验收步骤（两个终端、浏览器 Network 面板观察预检与响应头），并在 `frontend-api-integration` 规格中写明"以文件协议打开不受支持"这一已知限制。
- **[`configs/config.yaml` 进入版本库带来密钥泄露风险]** → C1 的配置项只有端口与来源白名单，无敏感信息；约定"密钥一律走环境变量、不进 `config.yaml`"写入配置模块注释，作为后续约束。
- **[优雅关闭的超时上限设得太短会切断正常请求]** → 默认值取一个明显宽裕的数值（如 10 秒），并通过配置项暴露，便于按实际调整。
- **[前端零构建意味着没有模块化与类型检查]** → 本变更前端仅有一个页面文件，规模可控；`frontend/index.html` 顶部注释写明"当页面逻辑增长时，应评估迁移到带构建的前端工程"，作为升级触发条件的提示。

## Migration Plan

本变更在空仓库上进行，无存量数据、无存量接口，因此不存在兼容性迁移。

落地顺序（与 `tasks.md` 一致）：模块与配置 → 公共机制（`platform`）→ 装配与进程入口（`bootstrap` + `cmd`）→ 领域实现（`health` + `destination`）→ 前端与 `Makefile` → 端到端人工验收。

回滚策略：全部为新增文件，`git` 层面直接丢弃即可；唯一被修改的既有文件是 `openspec/config.yaml` 与 `AGENTS.md` 的表述性内容，回滚时一并还原。

## Open Questions

- **前端是否需要从 `frontend/` 迁出为独立仓库**：若将来前端引入构建工具链，同仓库下的 `frontend/` 会与 Go 模块的工具链共存。当前按同仓库处理，待前端工程化时再评估。
- **`code` 分段中的 `401xx` / `403xx` 何时启用**：本变更不含认证，这两段暂无触发场景。待引入认证时再定义具体取值，届时分段规则已就绪。
- **是否引入 `golangci-lint` 等静态检查**：C1 不引入（`Makefile` 只提供 `fmt`）。若团队规模扩大或提交质量波动，再作为独立变更引入。
