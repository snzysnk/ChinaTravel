## Context

动机见 `proposal.md`。此处只记录决定实现方式的环境事实：

- 前端 `index.html:119` 的 `API_BASE` 当前为 `http://localhost:8080`，
  其上方注释自述"默认与 configs/config.yaml 中的端口保持一致"——意图正确，取值已漂移。
- 后端权威取值：`backend/configs/config.yaml` 的 `server.port: 18080`。
- `Makefile:11` 的 `BACKEND_PORT ?= 8080`，其注释写明"仅用于提示信息
  （真实端口由配置与环境变量决定）"——已自认不是权威，但取值同样过时。
- 前端是零构建静态页面，**没有环境变量机制**——这是排除若干方案的硬约束。
- 后端配置支持 `APP_` 前缀环境变量覆盖（如 `APP_SERVER_PORT=9090`），
  因此"后端实际监听的端口"在运行期是可变的，而前端的取值是构建期写死的常量。
  这个落差无法在本变更中消除。
- 本变更触及两个仓库：前端仓库（`index.html`）与 workspace 仓库（`Makefile`、规格）。
  后端仓库**不产生提交**。

## Goals / Non-Goals

**Goals:**

- 让页面在默认配置下端到端可用——健康检查与列表请求都能到达后端。
- 把"前端从何处得知后端地址"这条从未成文的约定写成规格，
  并指定唯一的权威来源。
- 消除 `Makefile` 提示值与实际端口不符带来的误导。

**Non-Goals:**

- **不为前端引入运行时配置机制。** 让 `API_BASE` 从外部注入（构建变量、查询参数、
  同源反代、静态服务的环境变量替换）都会破坏
  `frontend-api-integration` 既有 requirement「前端资源 SHALL 无需构建步骤」，
  属于另一个量级的改动，不在本次范围内。
- **不消除运行期覆盖带来的落差。** 用 `APP_SERVER_PORT` 覆盖端口后，
  写死的 `API_BASE` 仍会失配。本变更只保证**默认配置**下一致，
  并把权威来源写成规格，使这种漂移有据可依。
- **不改后端。** `server.port: 18080` 是正确的，本次是让前端与编排向它看齐。

## Decisions

### 决策 1：以前端对齐后端，而非以后端对齐前端

**理由**：三个人工产出的取值里，`backend/configs/config.yaml` 是唯一被**运行时真实读取**的
一处，其余两处（`index.html` 的常量、`Makefile` 的提示变量）都不参与程序行为。
把权威放在真正生效的地方，是唯一不会产生"改了不生效"困惑的选择。

**备选方案**：把后端 `server.port` 改回 `8080`，让前端的现值变成正确——
被否决。这会让后端为一个纯前端的笔误让步，且 `8080` 作为众多服务的常规端口，
保留一个不常见的 `18080` 反而降低了本机端口冲突概率。

### 决策 2：新增 requirement，而不是修改既有 requirement

**理由**：既有 5 条 requirement 描述的是前端"**怎么发请求、怎么解析信封、怎么渲染**"，
没有一条涉及"**发往哪里**"。地址来源是一条缺失的约束，用 ADDED 补进去；
若用 MODIFIED 改写某条既有 requirement，会把不相关的语义混进同一条，反而降低可读性。

`frontend-api-integration` 这个能力的 Purpose 已覆盖"前端页面与后端接口的对接约定"，
本条约束正落在该范围内，因此不新开能力。

### 决策 3：把权威来源写进规格，而不是只改数字

**理由**：本次缺陷的根因是取值在三处重复且无人负责。
只改数字，下次改后端配置时会原样复发。
把"`backend/configs/config.yaml` 的 `server.port` 是权威来源"写成 requirement，
并配一个"后端配置变更时其余取值随之更新"的 scenario，
使这条约束在被违反时可被指认为缺陷，而非风格偏好。

**取舍**：这会让每次改后端端口都变成一次**跨仓库改动**（改后端配置 + 改前端常量 +
改 Makefile 提示值 + 更新 workspace 的 submodule 指针）。
接受这一成本——跨仓库改动的繁琐是 submodule 拓扑的固有代价，
已被 `workspace-repo-topology` 规格承认；而"取值静默漂移"的代价更高。

## Risks / Trade-offs

- **[用 `APP_SERVER_PORT` 覆盖端口后页面仍失配]** → 已知且被 Non-Goals 显式接受。
  规格只要求默认配置下一致；运行期覆盖属于开发者主动偏离，需自行同步前端常量。
- **[改前端常量却忘记更新 workspace 的 submodule 指针]** → 提交顺序上把
  workspace 的 submodule 更新与前端提交绑定在同一次变更内；
  `git submodule status` 中该行以 `+` 开头即为指针落后，作为可检出的信号。
- **[同一事实仍分散在三处，未来仍可能漂移]** → 规格已指定权威来源，
  使漂移可被指认为违反 requirement；彻底的单一来源方案需要前端支持构建或反代，
  与「无需构建步骤」冲突，见 Non-Goals。
- **[`Makefile` 的 `BACKEND_PORT` 不参与任何命令，纯提示]** → 保留但不改其性质。
  本次只让它与权威来源一致；若将来它被用于实际命令，需重新评估是否应改为从配置文件读取。

## Migration Plan

无数据迁移。两个仓库各一次提交，无回滚风险——改动是单个常量与一处提示变量，
回退即还原取值。

执行顺序（跨仓库，顺序有意义）：

```
① 前端仓库  index.html   API_BASE 8080 -> 18080，注释补权威来源说明
            git commit && git push
                v
② workspace  Makefile    BACKEND_PORT 8080 -> 18080
            submodule 指针更新到 ① 的新提交
            git commit && git push
```

先改前端再更新指针，可避免 workspace 提交出一个指向"尚未推送的提交"的指针。
