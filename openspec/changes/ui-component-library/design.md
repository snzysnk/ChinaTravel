## Context

动机与范围见 `proposal.md`。此处只记录影响技术选择的现状与约束。

- 工程形态：Vue 3.5 + TypeScript 5.7 + Vite 6，入口 `frontend/src/main.ts` 目前仅
  `createApp(App).mount('#app')` 与引入全局样式两件事。
- 当前界面只有 `src/views/DestinationHome.vue`（142 行）与 `App.vue`（14 行），
  样式分布在 `src/assets/main.css`（CSS 变量定义）、`src/assets/page.css`（卡片/按钮/状态胶囊）
  与组件的 `<style scoped>`（列表专用样式）三处。
- 类型检查是构建的前置门禁：`npm run build` = `vue-tsc --noEmit && vite build`；
  `tsconfig.json` 开启了 `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`
  与 `verbatimModuleSyntax`，对类型声明质量要求较高。
- `vite.config.ts` 已承载 `BACKEND_PORT`（18080）与 `DEV_SERVER_PORT`（5174）两个常量，
  且 `frontend-toolchain` 规格规定转发目标必须与后端 `server.port` 一致、前端源码不得出现
  后端端口。新增插件配置必须与这两个常量互不干扰。
- 协作模式（沿用 `frontend-stack-and-toolchain` 决策 1）：AI 生成代码、单人审阅与维护，
  首要指标是「错误是否暴露在阅读层面」。
- 前端是独立 Git 仓库，改动落在此仓库；workspace 仓库仅更新 submodule 指针。

## Goals / Non-Goals

**Goals:**

- 选定并引入单一 UI 组件库，使后续新增界面不再手写交互元素。
- 控制引入成本：产物体积只随实际用量增长；主题定制只有一个入口；不破坏既有类型检查强度。
- 既有页面的链路验收能力不变——替换后页面行为可逐项对照替换前。

**Non-Goals:**

- 不引入路由、状态管理、CSS 框架、测试框架（触发条件见
  `frontend-stack-and-toolchain` 的 `design.md` 决策 5）。
- 不重做视觉设计。本变更的界面改动限于「手写元素换成组件库组件 + 消除重复样式」，
  不借机调整配色、间距或布局。
- 不新增业务功能，不新增接口。
- 不处理组件的无障碍（a11y）深度定制——采用组件库默认行为。
- 不建立组件库的版本升级策略，留待实际遇到升级需求时处理。

## Decisions

### 1. 选型：Element Plus（对比 Naive UI / Ant Design Vue / TDesign Vue Next）

**结论**：采用 Element Plus。

**评估维度与实测数据**（四个候选均为 Vue 3 原生实现；数据于 2026-10-03 通过
npm registry 与 GitHub API 实时查询，非记忆）：

| | Element Plus | Naive UI | Ant Design Vue | TDesign Vue Next |
|---|---|---|---|---|
| 最后发版 | 2026-09-30 | 2026-08-27 | **2024-11-11** | — |
| 周下载量 | 713,389 | 252,578 | 230,346 | 56,979 |
| Stars | 27,794 | 18,565 | 21,671 | 2,191 |
| 近 365 天提交 | 100+ | 100+ | **12**（10 条为 docs/ci/赞助位）| — |

**理由**：本项目的首要指标是「错误是否暴露在阅读层面」而非「一次写对的概率」，
在这一前提下，「遇到问题时能否搜到答案」的权重高于「源码是否优雅」——

- Element Plus 的周下载量约为 Naive UI 的 2.8 倍、TDesign 的 12.5 倍，
  意味着遇到非预期行为时大概率已有现成答案。单人维护下，「搜不到就只能自己读源码」，
  而这正是本项目最想避开的工作。
- 复杂场景（多级表头、合并单元格、固定列、表单校验体系）Element Plus 的覆盖面最完整，
  国内中后台的「难做的表格」基本有现成解法。
- 中文文档、`zh-cn` locale 与国内中后台视觉默认值开箱即用。

**已考虑的替代**：

- **Naive UI（次选，加权分几乎持平）**：优势是主题用 JS 对象声明、无 Sass 编译链，
  「改样式不碰构建配置」的收益是真实的。被否的原因是**语料与生态差距无救济手段**，
  而 Element Plus 的「改主题要懂 SCSS 覆盖链」这一劣势有救济手段——见决策 4，
  只在设计变量层覆盖、不做深度穿透即可绕开大部分成本。若本项目的 UI 定制程度显著提高
  （不愿被组件库默认视觉约束、主题需频繁调整），应重新评估本决策。
- **Ant Design Vue（排除）**：最后一条代码提交停在 2026-02-27，最后发版 2024-11-11，
  即已 23 个月无代码发布。**排除理由与代码质量无关，而是周期性维护已停止**——
  引入它等于承接一份无人修复的负债。其 open issues 数量较低（128）是「无人处理」的结果，
  不构成质量信号，不可反向解读。
- **TDesign Vue Next（排除）**：设计规范与中文适配本身达标，但周下载量约为 Element Plus
  的 1/12，语料最少，AI 生成时更容易编造不存在的 props；遇到问题几乎只能读源码。

**代价（必须被接受，而非忽略）**：Element Plus 使用 SCSS 变量做主题，深度定制需要理解
Sass 覆盖链；其组件内部样式较重，覆盖时常需 `:deep()` 穿透。缓解方式是决策 4 的
「只在设计变量层覆盖」约束。

### 2. 按需引入：unplugin-vue-components + unplugin-auto-import

**结论**：使用两个 unplugin 插件实现组件与样式的按需自动引入，不做全量注册。

**理由**：全量注册（`app.use(ElementPlus)`）会把约全部组件的代码与样式纳入产物，
而本项目实际用到的组件数在个位数到十几个之间，产物中绝大部分是死代码。按需引入使
体积只随用量增长，也避免了「引入一个按钮导致首屏多几百 KB」这类不可见成本。

**已考虑的替代**：

- 全量注册：配置最简单，但放弃体积控制，且与「不引入非必需依赖」的项目条款精神相反。
- 手工逐个 `import` 组件与样式：控制最精确，但每次使用组件都要写两行 import，
  且漏写样式时表现为「组件无样式」这类难以定位的问题；在 AI 生成场景下这是高频失误点。

**代价**：两个插件是构建期依赖，且会生成自动导入的类型声明文件。
需在 `tsconfig.json` 的 `include` 中确保该声明文件被纳入类型检查，否则
「组件无需手工 import」会与 `vue-tsc` 报「找不到名称」冲突——这是本决策最需要验证的一点。

### 3. 图标：声明 `@element-plus/icons-vue`，但不全局注册

> **本条已修订。** 原结论为「全局注册组件」，在实现阶段经实测证伪后改为此结论，
> 判定依据是决策 2 的按需原则与产物体积实测值，不是偏好。修订留痕于此，不抹去原判断。

**结论**：把官方图标包声明为依赖，**不**在入口全局注册；页面用到哪个图标就引哪个。

**理由**：组件库内置交互所需的图标，由 element-plus **自己**从这个包取用——
`@element-plus/icons-vue` 出现在 element-plus 的 `dependencies` 中（不是 peerDependencies），
可关闭标签的关闭图标、下拉展开箭头、表单校验状态图标、日期面板翻页箭头都是这么来的。
也就是说，这些内置交互**不依赖我们注册任何东西**。声明该依赖的意义因此收窄为：
页面自己要写图标时，有与组件库同一套、版本对齐的图标可用，不必另找图标来源。

**已考虑的替代**：

- **全局注册全部图标（本条的原方案）**：被否。实测使产物 JS 由 309,198 B 增至
  475,165 B（**+165,967 B，+53.7%**），而当前没有任何页面直接使用图标——为「将来可能用到」
  预先付出过半的产物体积，与决策 2「按需」的目标直接相反。
- **不声明图标包**：被否。原方案给出的理由（内置交互缺图标会退化成空缺样式）经复核
  **不成立**——见上。保留声明是因为它没有额外成本：它本就是 element-plus 的传递依赖，
  且按需引用的图标可被正常 tree-shake，未用到的不会进入产物。

**代价**：页面写图标时需要显式 `import`，失去「标签直接可用」的便利。这是可接受的——
显式 import 让「这个图标从哪来」在阅读层面可见，与本项目「错误是否暴露在阅读层面」
这一首要指标一致。

### 4. 主题定制：只覆盖设计变量，不做穿透

**结论**：定制集中在单一文件内，通过组件库的设计变量覆盖与会话级 `size` / `z-index`
等全局配置入口声明；页面不得对组件内部样式做视觉类穿透。

**理由**：这条直接落实「源码容易更改」这一维度——把「改全站主色」从「需要在多处
SCSS 变量与组件样式中查找」变成「定位一个文件」。同时避免手写样式与组件库样式两套体系
并存导致的覆盖优先级不可推理。

**已考虑的替代**：逐个组件用 `:deep()` 穿透调整。被否——穿透选择器与组件库内部 DOM 结构
耦合，组件库小版本升级就可能失效，且失效时表现为「样式静默变样」而非报错。

**边界**：布局类调整（宽高、间距、flex 排列）仍可在页面局部样式中书写；被禁止的是
视觉类覆盖（颜色、圆角、阴影、字号）。二者的区分标准是「是否可由设计变量表达」。

### 5. 既有页面迁移：原样替换，行为对齐

**结论**：`DestinationHome.vue` 的三种列表态、健康状态三态、失败态与「重新加载」交互
逐一保留，只把手写结构换成组件库组件；`page.css` 中与组件库职责重叠的部分（按钮、
空态、错误提示样式）移除。

**理由**：沿用 `frontend-stack-and-toolchain` 决策 7 的方法论——迁移与改进混在一起时，
出问题无法判断是「迁移引入的」还是「新逻辑的 bug」。原样替换把变量收敛为一个：
链路是否仍然完整。验收标准因此是客观的（逐项对照替换前），而非「看起来没问题」。

**已考虑的替代**：借引入组件库的机会重做页面。被否——与本变更的 Non-Goals 冲突，
且会让「组件库是否可用」与「新设计是否可行」两个问题纠缠在一起。

### 6. 目录落位：组件层拆分

**结论**：可复用组件放 `src/components/`，仅单页使用的片段留在页面目录内，
不在本变更中提前抽取组件。

**理由**：当前只有一个页面，按 YAGNI 不制造空的组件目录与「为了用而抽」的组件。
本决策确立的是**规则**（何时该抽、抽到哪），而非在本次产出具体组件。该规则落实
`frontend-toolchain` 规格中「可复用组件位于约定目录」的约定。

## Risks / Trade-offs

- **提前引入违背自身 YAGNI 条款** → 决策在知情前提下作出并记录在 `proposal.md` 的 Why 中；
  缓解方式是限制引入范围（不做全量注册、不引入配套的 CSS 框架与测试框架），
  使沉没成本可控。**若后续发现组件库未被实际使用，回退成本是移除依赖 + 恢复手写样式，
  而非重写业务逻辑。**
- **按需引入与 `vue-tsc` 的类型声明冲突** → 这是本次最可能踩的坑（见决策 2 的代价）。
  缓解：把「`npm run typecheck` 在引入插件后仍然通过」列为必须验证项，且验证方式是可执行命令
  而非目视检查。
- **SCSS 主题覆盖链的理解成本** → 缓解：决策 4 限定只覆盖设计变量，不做穿透；
  若实际需要深度定制，届时以独立变更评估是否切换到 JS 对象主题的组件库（见决策 1 的次选）。
- **组件库版本升级导致视觉漂移** → 本变更不处理升级策略（Non-Goals）；
  风险记录于此，待真实遇到升级需求时以独立变更处理。
- **`vite.config.ts` 被改动时误伤端口常量** → 缓解：`frontend-toolchain` 规格已有
  「前端制品中不含后端端口」场景，任务中包含对此的复核步骤；插件配置与端口常量在文件中
  分区书写并加注释说明互不相关。
- **产物体积虽然按需，仍会大于手写 CSS** → 接受。收益（不再手写交互元素、
  交互语义一致）大于代价；体积可通过构建产物大小对比观测，作为任务的验证项之一。

## Migration Plan

1. 引入依赖与插件配置，确保 `npm run typecheck` 与 `npm run build` 均通过（此时页面未改，属纯增量）。
2. 引入语言包与主题覆盖文件，确认构建仍通过。
3. 替换 `DestinationHome.vue` 的手写元素，同步清理 `page.css` 中的重复样式。
4. 逐项对照替换前的页面行为做人工验收（三态、空集合、失败、重新加载）。
5. 记录替换前后的构建产物大小，作为本变更的成本证据。

**回滚策略**：本变更是前端仓库内部的依赖引入与页面改写，回滚即还原到替换前的提交。
因不涉及接口契约与后端，回滚不影响链路可用性。建议在替换页面（第 3 步）之前
提交一次「引入依赖但未改页面」的状态，使「引入组件库本身是否出问题」可独立回滚。
